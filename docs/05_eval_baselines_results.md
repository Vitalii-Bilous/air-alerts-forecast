# Крок 2. Каркас оцінки: код, тести, метрики базових прогнозистів на validation

Код лежить у [`alerts_forecast/`](../alerts_forecast/). Test **не відкривали**: без прапорця `--final-test` код обрізає дані на 2026-09-12 00:00 за Києвом ще до побудови сітки.

## Як запустити локально

```bash
cd alerts_forecast
pip install -r requirements.txt
# покласти volunteer_data_en.csv у data/ (посилання raw.githubusercontent.com з кроку 1б)
python -m pytest -q tests                                                  # 11 passed, 1 skipped
ALERTS_CSV=data/volunteer_data_en.csv python -m pytest -q tests            # 12 passed (+ тест на реальних даних)
python run_eval.py --data data/volunteer_data_en.csv                       # ~2 хв → results/
```

Мої результати: тести `12 passed in 12.21s`, `run_eval.py` близько 1 хв 50 с. Вивід збережено в `results/val_run_log.txt`.

## Тести

| Тест | Що перевіряє |
|---|---|
| `test_labels_and_features_by_hand` | мітки й ознаки на ручному прикладі: межі `[t, t+H)`, відбій, naive-тривога, київська година (UTC+2 у січні) |
| `test_features_unchanged_when_future_perturbed` ×4 | **ознаки** для будь-якого t0 (4 значення, зокрема з хвилинами): усі події після t0 замінено випадковими, кінці незакритих до t0 тривог змінено, а ознаки для t ≤ t0 мають лишитись ідентичними. Контроль: після t0 ознаки змінюються, тобто тест не «сліпий» |
| `test_features_unchanged_on_real_data` | те саме на реальних даних (6 регіонів, 2 значення t0), запускається, якщо задано `ALERTS_CSV` |
| `test_predictions_unchanged_when_future_perturbed` ×2 (H=1, 3) | **прогнози** всіх 4 базових моделей: у кожному з 4 фолдів t0 вибирається випадково **після межі навчання фолду**; прогнози для t ≤ t0 мають бути ідентичними |
| `test_fold_boundaries_and_purge` ×2 | 4 фолди; `max(t_train) + H ≤ початок фолду`; оцінка в межах фолду; purge на кінці періоду; усі старти, що визначають мітки train, < початку фолду |
| `test_long_alert_mask_uses_only_info_known_at_cutoff` | маска довгих тривог для train не знає майбутньої тривалості; Донецька не маскується |
| `test_cut_events_locks_future` | «замок»: після cutoff не лишається жодного старту чи кінця |

**Чи ловлять тести справжній leakage.** Я навмисно вносив витоки в копію коду і щоразу дивився, чи тести падають:

| Внесений виток | Результат |
|---|---|
| прибрав purge у train | падає `test_fold_boundaries_and_purge` |
| `rate28` бачить мітку на 1 год раніше, ніж можна | падають 5 тестів |
| ознаки бачать старти на 30 хв уперед | падають 3 тести |

## Що змінилося відносно дизайну (важливо)

1. **Naive-тривоги: без обмеження 6 год.** Тести показали: якщо обмежувати 6 годинами лише naive-тривоги, це вже leakage. У реальному часі naive-тривога (відбій так і не прийшов) нічим не відрізняється від звичайної, що ще триває. Те, що відбою «не буде», стає відомо лише заднім числом. Тому тепер для всіх тривог однаково: тривога активна, доки не надійде відбій або наступний старт. Обмеження 6 год лишилося лише в ознаці `minutes_since_start`.
2. **Маска довгих тривог на train рахується станом на початок фолду.** Інакше рішення «викинути рядок» залежало б від того, чи тривога, що почалася до межі, триватиме понад 6 год, а це стає відомо лише після межі. Naive-тривога, після якої ще не було старту, на межі вважається такою, що триває.
3. `rate28h` (та сама година доби) рахується зсувом на 24·k год в UTC. Протягом 28 днів після переходу на літній чи зимовий час це дає зсув на одну годину відносно київської доби. Простота тут важливіша.
4. `log_loss` і Brier рахую вручну, з обрізанням ймовірностей до [1e-6, 1−1e-6], щоб не залежати від версії sklearn. Зі sklearn беру лише `average_precision_score` (PR-AUC).

## Що видно (це лише базові прогнозисти)

- **Найсильніший базовий прогнозист — `clim_28d`.** Частота за весь train (`clim_train`) гірша на 8% Brier для H=3 (BSS −0.083 [−0.110, −0.059]). Якщо train брати з 2022, вона гірша вже на 33%. Це прямий наслідок дрейфу 2026 року.
- **`clim_28d_hour` дає виграш лише на фронті:** BSS +0.023 [+0.007, +0.039] для H=3. У центрі він гірший (−0.019), на заході різниця в межах шуму. Тобто сезонність за годиною доби слабка й неоднорідна по групах.
- **`recent_start` не допомагає,** а на фронті й у центрі шкодить. Сам факт старту за останні H годин без контексту мало що каже.
- **Калібрування при H=3:** у середньому діапазоні (прогноз 0.2–0.5) спостережена частота вища за прогноз на ~0.05–0.1. Тобто навіть 28-денна частота запізнюється за ростом активності.
- **Захід:** base rate 0.065 / 0.023 і ДІ ширші за будь-яку різницю між моделями. Висновки для заходу будуть найслабшими.
- **Додаткова метрика без довгих тривог:** маска прибирає для H=3 лише 222 з 14 070 рядків: Тернопільська 127, Івано-Франківська 81, Черкаська 14. Brier змінюється в 3-му знаку, висновки ті самі.
- **Ціль для моделей наступного кроку:** обійти `clim_28d`, тобто BSS > 0 з ДІ, що не перетинає 0. Окремо для фронту й центру, при H=3 і H=1.

## Як перевірити

1. `python -m pytest -q tests` → 11 passed, 1 skipped; з `ALERTS_CSV=...` → 12 passed.
2. `python run_eval.py --data data/volunteer_data_en.csv`. Перший рядок має закінчуватися на `last start: 2026-09-11 20:55:09+00:00` (жодного старту з test), а таблиця має збігтися з наведеною вище до 4-го знаку.
3. Для H=3 `n` дорівнює 14 070 = 21 × 670: purge на кінці validation прибирає 2 останні години в кожному регіоні. Для H=1 маємо 21 × 672, бо `t + 1 год ≤ кінець` виконується для всіх годин.
4. **Leakage:** відкрити `alerts/features.py` і переконатися, що кожна ознака використовує `searchsorted(..., t, "left")` (старти строго < t) або `shift(H)` для міток. Потім самому внести виток (наприклад, `shift(H - 1)`) і подивитися, як падають тести.
