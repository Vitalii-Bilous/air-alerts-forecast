# Прогноз старту повітряної тривоги в області

Модель щогодини оцінює ймовірність того, що в області **почнеться нова повітряна тривога протягом наступних H годин**. H=3 — основний горизонт, H=1 — додатковий. Прогноз робиться для 21 області. Оцінка — на останніх 4 тижнях даних (12.09–10.10.2026), без жодного підглядання в майбутнє.

**Результат на test (один прогін):** градієнтний бустинг кращий за найсильніший бейзлайн, тобто частоту тривог у регіоні за останні 7 або 28 діб, на **4.5–4.8% Brier** при H=3 і на **4.0–4.2%** при H=1. 95% довірчі інтервали не перетинають нуль, і модель краща в кожному з 4 тижнів test. Виграш скромний і майже повністю йде від регіональної динаміки тривог. Найбільший він тоді, коли тривога вже триває. Першу тривогу після тихої доби модель не передбачає.

## 1. Постановка

- **Об'єкт:** пара (область, година t) на погодинній сітці UTC.
- **Ціль:** `y_H(t) = 1`, якщо в області стартує тривога в інтервалі `[t, t+H)`. Модель видає ймовірність, тобто це ймовірнісна класифікація, а не прогноз кількості.
- **Чому саме так:** на це питання є практична відповідь («чи буде тривога найближчим часом»), і для нього є чесні метрики (Brier, калібрування). Чому не обрано тривалість чи кількість тривог, пояснено в [docs/01](docs/01_problem_framing.md).
- **Групи регіонів** зафіксовано за географією ще до результатів: фронт 8, центр 8 (з Одеською), захід 5. При H=3 на фронті задача майже тривіальна (base rate до 0.9 у Харківській і Дніпропетровській), тому H=1 рахуємо окремо.
- Година доби й день тижня беруться за київським часом.

## 2. Дані та їхні проблеми

Джерело: [Vadimkin/ukrainian-air-raid-sirens-dataset](https://github.com/Vadimkin/ukrainian-air-raid-sirens-dataset). Основний набір — волонтерський eTryvoga (`volunteer_data_en.csv`: `region, started_at, finished_at, naive`), бо офіційний закінчується 2026-09-07. Офіційний набір використано лише для перевірок. Знімок даних від 2026-10-11 лежить у `data/` (sha256 `e441ecaa9813c908…`), бо датасет оновлюється щодня.

Перед моделюванням дані перевірено: [docs/02](docs/02_data_checks.md), [docs/03](docs/03_data_fixes_and_long_alerts.md), скрипти в `docs/checks/`.
- **Львівська з 11.2025 і Волинська з 09.2025 зіпсовані.** Їхні волонтерські тривоги збігаються з тривогами в окремих районах Одеської (0.71) та Чернігівської (Прилуцький район, 0.88) областей. Це в ~15 разів частіше за випадковий збіг і в ~4 рази частіше, ніж у контрольних областей. Обидві області виключено.
- **Закарпатська:** після 2026-07-30 немає жодної тривоги, хоча в офіційних даних у серпні їх 12. **Луганська:** лише 3 записи. Обидві виключено. Лишається **21 область**.
- **«Завислі» відбої:** у західних областях трапляються тривоги на 70–94 години. Тривоги довші за 6 год вважаємо пропущеним відбоєм і прибираємо відповідні рядки **лише з train**. Виняток — Донецька й Запорізька, де довгі тривоги справжні. На validation і test основна метрика рахується на **всіх** годинах, бо в реальному часі довжину тривоги не знати. Додатково наводимо метрику без цих годин.
- `naive=True` означає, що кінець тривоги вигаданий (+30 хв). Таку тривогу вважаємо активною до наступного старту.
- У 2026 році активність сильно зросла, і дані з 2022 року шкодять. **Train починається з 2025-12-01** (обрано на validation).

## 3. Оцінка без leakage

| Період | Дати (Київ) | Як використано |
|---|---|---|
| train | 2025-12-01 … 2026-08-15 | навчання |
| validation | 2026-08-15 … 2026-09-12 | вибір моделей і рішень |
| test | 2026-09-12 … 2026-10-10 | **відкрито один раз**, після письмово зафіксованої гіпотези ([docs/09](docs/09_pretest_hypothesis.md)) |

- **Щотижневе перенавчання (rolling origin).** 4 фолди по тижню. Для кожного тижня модель навчається на всіх даних з 2025-12-01 до його початку. На межі фолду робимо purge на H годин, щоб мітка останнього рядка train була вже відома.
- **Ознаки лише з минулого:** старти до t і кінці тривог, відомі до t. Частоти рахуються з міток, уже відомих у момент t (`shift(H)`). Маска довгих тривог на train визначається станом на початок фолду.
- **Гіперпараметри й ваги свіжих даних** обираються в кожному фолді на внутрішньому часовому спліті (останні 14 днів train фолду), а не на validation чи test. Early stopping бустингу теж часовий, а не випадковий.
- **Автотести** (`tests/test_leakage.py`). Головний — тест «зіпсуй майбутнє»: події після t0 видаляються або змінюються, а ознаки (для будь-якого t0) і прогнози всіх моделей (для t0 після межі фолду) мають лишитися ідентичними. Окремо перевіряються межі фолдів і purge, маска довгих тривог «станом на t» і замок на test. Мутаційна перевірка показала, що тести ловлять навмисно внесений leakage.
- **Замок на test:** без прапорця `--final-test` код відрізає всі події після кінця validation ще до побудови сітки.

**Метрики:** Brier (основна) і Brier skill score (BSS) відносно `clim_28d`, референс обрано заздалегідь. Також log loss, PR-AUC і калібрування (ECE, 10 бінів). 95% довірчі інтервали отримано блочним bootstrap по добах (1000 повторів).

## 4. Моделі

| Назва | Що це |
|---|---|
| `clim_28d` | частка годин зі стартом у регіоні за останні 28 діб (референс BSS) |
| `clim_7d` | те саме за 7 діб; на validation найсильніший бейзлайн |
| `clim_28d_hour`, `clim_train`, `recent_start` | інші прості бейзлайни |
| `logreg` | логістична регресія: стандартизація, sin/cos часу, one-hot регіону, L2 |
| **`hgb`** | `HistGradientBoostingClassifier` зі sklearn, **основна модель** |

Обидві моделі спільні для всіх 21 регіону. Ознаки (`alerts/features.py`):
- регіональні: чи активна тривога в t, хвилин від її початку, годин від останнього старту, кількість стартів за 1/3/24/168 год, частоти за 7 і 28 діб, частота для тієї ж години доби;
- по країні й групі: скільки регіонів зараз під тривогою, кількість стартів за останні 1–24 год;
- година й день тижня.

| 3 | logreg | 0.1757 | +0.043 [+0.030, +0.055] | | 0.026 |
| 3 | **hgb** | **0.1753** | **+0.045 [+0.030, +0.060]** | **+0.048 [+0.032, +0.065]** | 0.017 |
| 1 | clim_28d | 0.1583 | 0 | | 0.014 |
| 1 | logreg | 0.1525 | +0.037 [+0.029, +0.044] | | 0.007 |
| 1 | **hgb** | **0.1519** | **+0.040 [+0.031, +0.049]** | **+0.042 [+0.030, +0.052]** | 0.007 |

Без годин довгих тривог цифри майже ті самі: для H=3 hgb дає +0.045 [+0.031, +0.059].

### Де модель корисна (test, hgb проти clim_7d)

| Ситуація | H=1 | H=3 |
|---|---|---|
| тривога в регіоні вже триває (32% годин) | +0.094 [+0.071, +0.119] | +0.059 [+0.037, +0.084] |
| у регіоні тихо (68%) | +0.024 [+0.012, +0.034] | +0.042 [+0.023, +0.064] |
| за добу не було жодного старту (11%) | +0.015 [−0.028, +0.061] | −0.014 [−0.073, +0.034] |

По групах (H=3, проти `clim_28d`): фронт +0.070, центр +0.036, захід +0.013 (ДІ перетинає 0). Деталі по тижнях і регіонах наведено в [docs/10](docs/10_test_results.md).

### Висновки
1. **Гіпотези, записані до test, підтвердились:** hgb кращий за обидва бейзлайни при H=3 і H=1. На validation у тиждень сплеску модель програла `clim_7d`, але на test цей ризик не справдився.
2. **Не підтвердилось:** перевага бустингу над логістичною регресією. На test вони рівні, тож виграш дають **ознаки**, а не вибір моделі.
3. Головне, що вивчила модель, — **механіка послідовного потоку тривог**: поки тривога триває, новий старт протягом години менш імовірний. Бейзлайни цього не бачать.
4. Ознаки по країні майже нічого не дають: в ablation на validation лише +0.005 BSS ([docs/08](docs/08_validation_analysis.md)). Їх залишено, щоб не підганяти модель під validation.

## 6. Обмеження

- **Ціль — волонтерський потік eTryvoga, а не офіційні дані.** У серпні 2026 лише 46% його стартів збігаються з офіційним стартом у межах ±3 хв, а 21% припадають на вже активну офіційну тривогу. Модель прогнозує саме цей потік.
- **Агрегати test-періоду я бачив до відкриття test:** на етапі перевірки даних я дивився помісячні кількості тривог за вересень. Рішень на них не ухвалював, але test не є повністю «сліпим».
- 4 тижні test замало для висновків про окремі регіони. Київська й Тернопільська на validation були серед найкращих, а на test трохи гірші за `clim_7d`.
- Активність сильно дрейфує, тож модель треба регулярно перенавчати. Протокол оцінки так і робить, щотижня.
- Для Львівської, Волинської, Закарпатської й Луганської прогнозу немає: ці області виключено.

## 7. Текстові дані (не реалізовано)

Тексти (новини, Telegram, офіційні заяви) свідомо не додано: за наявний час ризик leakage був більший за можливий виграш. Щоб додати їх чесно, треба:
1. Брати лише повідомлення з **часом публікації < t**, а не з часом події, про яку йдеться. Відредаговані дописи брати в першій версії.
2. Агрегувати їх в ознаки на сітці (регіон, година), наприклад кількість згадок «шахед» чи «пуск» за останню годину по регіону. Рахувати тим самим кодом «станом на t».
3. Додати ці ознаки в тест «зіпсуй майбутнє»: повідомлення після t0 не мають змінювати ознаки до t0.
4. Не брати джерела, які публікують уже після початку тривоги (наприклад, підсумкові звіти), без перевірки затримки публікації.

## 8. Як запустити

```bash
pip install -r requirements.txt     # перевірено на Python 3.13, scikit-learn 1.9.1, pandas 3.0.5, numpy 2.5.3
python -m pytest -q tests                                          # 11 passed, 1 skipped (~2 хв)
ALERTS_CSV=data/volunteer_data_en.csv python -m pytest -q tests    # 12 passed (з тестом на реальних даних)
python run_eval.py --data data/volunteer_data_en.csv               # validation, ~5 хв → results/val_*
python analysis/analyze_val.py --data data/volunteer_data_en.csv   # ablation і зрізи validation, ~3 хв
python run_eval.py --data data/volunteer_data_en.csv --final-test  # test (відтворення; вже прогнано один раз)
python analysis/summarize_test.py                                  # парні порівняння й зрізи test
```

Для часового early stopping бустинг передає `X_val`/`y_val` у `HistGradientBoostingClassifier.fit`. Якщо ваша версія sklearn цього не підтримує, оновіть її.

results/      метрики, прогнози, графіки калібрування (val_* і test_*)
